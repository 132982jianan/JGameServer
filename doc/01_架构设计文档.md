# JGameServer 实际架构设计

> 本文只描述当前仓库已经落地的代码，更新时间：2026-09-14。

## 1. 系统边界

JGameServer 使用 Kotlin/JDK 21、Akka Classic、Nacos、MongoDB 和少量 Redis，实现无区服、无密码 LoginDebug 的多人游戏服务端。所有服务编译为同一个 `server-all.jar`，以 `--kind` 和 `--id` 启动不同进程。

| NodeKind | 职责 | 默认端口 |
| --- | --- | --- |
| `portal` | 从 Nacos 分配 Gate | HTTP 8080（容器映射） |
| `gate` | Netty WebSocket、连接级 GateActor、协议路由 | Artery 25000、WS 25002 |
| `lobby` | Account、Player 生命周期和玩家私有业务 | Artery 30000 |
| `battle` | 战斗规则和一局一个 BaseBattleActor | Artery 40000 |
| `global` | 匹配、战局目录、在线摘要、聊天和房间 | Artery 50000 |
| `insight` | 简化管理面 | Artery 60000、HTTP 9000 |

项目永远不使用 Akka Cluster Sharding。Gate/Lobby/Battle 通过 NodeKind + NodeId 横向扩容，Global 首版单实例；Nacos 负责发现，Akka Remote 负责通信。

## 2. 模块与依赖

```text
common/             协议、Akka/协程、Nacos、Mongo/Redis 基础设施、Db 实体
portal/             Gate 分配 HTTP
gate/               Netty 和 GateActor
lobby/              AccountActor、PlayerActor
global/             Match/BattleDirectory/Chat/Room Actors
battle/             BattleServerActor、BaseBattleActor
insight/            管理 HTTP
server/             唯一启动入口和 fat jar
TicTacToe-GUI/      演示客户端
```

DB 封装已合入 common。服务模块之间没有 Gradle 业务依赖，运行时只通过共享协议与远端 ActorRef 协作。

## 3. 进程启动

统一入口为 `server/src/main/kotlin/com/jacey/game/server/Application.kt`：

```text
解析 --kind / --id
  -> Application 按 NodeKind 调用 XxxStart.start(id)
  -> XxxStart 调用 common/CommonStart.start(kind, id)
  -> 日志与退出信号
  -> Nacos 初始化和 NodeKind/NodeId 注册
  -> Akka ActorSystem
  -> 按节点初始化 Mongo/Redis
  -> XxxStart 初始化本节点 Actor / HTTP / Netty
  -> Application 标记 Nacos 节点启动完成
```

| 节点 | Nacos | MongoDB | Redis |
| --- | --- | --- | --- |
| Portal | 是 | 否 | 否 |
| Gate | 是 | 否 | 否 |
| Lobby | 是 | 是 | 否 |
| Global | 是 | 否 | 否 |
| Battle | 是 | 是 | 否 |
| Insight | 是 | 是 | 是，仅 token TTL |

在线、匹配、战局、房间和棋盘都不使用 Redis。Redis 目前仅服务 Insight 登录 token。

## 4. Akka ActorId + ActorState 模式

参考 `code` 的 ActorId 是领域身份，ActorState 是该 Actor 独占的可变状态。Akka 版采用以下等价实现：

- ActorId 用于节点内目录查找，并编码为合法 Akka actor path。
- ActorState 是 Actor 内部 data class/私有字段，禁止其它 Actor 直接修改。
- 节点根 Actor 是跨进程入口；`NodeKind + NodeId` 经 Nacos 找到根 ActorRef。
- `CoroutineActor` 内部单协程串行消费消息，挂起数据库或 `askAwait` 时不占线程。
- 不把 ActorPath、ActorRef 或临时路由写数据库。

| Actor | 领域 ActorId | ActorState |
| --- | --- | --- |
| LobbyRootActor | Lobby 固定单例 | AccountId/PlayerId→ActorRef 目录 |
| GateActor | connectionId | Channel、sessionId、AccountId、PlayerId、LobbyId |
| AccountActor | AccountId | DbAccount、GateActorRef、PlayerActorRef |
| PlayerActor | PlayerId | DbPlayer、GateActorRef、保存心跳 |
| MatchActor | Global 固定单例 | 匹配队列、matchingPlayerIds |
| BattleManagerActor | Global 固定单例 | PlayerId→BattleLocation、BattleId→Players |
| ChatActor | PlayerId | 当前 GateActorRef |
| RoomActor | BattleId | 允许成员、已加入成员 |
| BaseBattleActor | BattleId | 玩家、棋盘、回合、事件、准备状态、GateActorRef |

## 5. Portal 与 Gate

Portal 只提供 `GET /gate`。它按客户端 IP 从健康 Gate 列表稳定选择一个节点，返回 `websocketEndpoint`；没有健康 Gate 时返回 503。Portal 不接收 LoginName，不创建账号，不签发票据。

Netty 建立连接时立即创建一个 GateActor 和 GateActorState。Channel attribute 只保存这一个 ActorRef，没有 ClientSession、ClientSessionManagerService 或 GateResponseActor。

客户端入站消息包装为 GateClientMsg，业务节点回包使用 NetMessage，因此同一 GateActor 能明确区分上下行：

```text
Netty -> GateClientMsg -> GateActor -> Lobby / Global
Lobby / Global / Battle -> NetMessage -> GateActor -> Netty Channel
```

路由规则：

| 协议 | 目标 |
| --- | --- |
| Login | AccountId 稳定哈希选择的 Lobby |
| Heartbeat | 已绑定 Lobby 的 PlayerActor |
| Match、CancelMatch | Global MatchActor |
| 战斗号段 | Global BattleManagerActor，再到目标 Battle |
| 聊天号段 | Global ChatManagerActor/RoomManagerActor |

断线时 Netty 向 GateActor 发送 GATE_DISCONNECTED，GateActor 通知 Lobby AccountLogout 后自行停止。

## 6. Account 与 Player

```text
AccountId = "LoginDebug_" + loginName.trim()
PlayerId  = Mongo Player sequence
```

DbAccount 表示登录身份、当前 Lobby 占有和 PlayerId 绑定。DbPlayer 表示角色聚合根，包含 account/basic/inventory 子数据；背包、任务等新增玩家私有业务均由 PlayerActor 串行处理。

登录时：

1. LobbyRootActor 使用自己的 LobbyRootActorState 按 AccountId 定位 AccountActor；子 Actor 终止后通过 watch/Terminated 清理目录。
2. AccountActor 创建/加载 DbAccount；新账号立即分配一个 PlayerId，并请求 LobbyRootActor 取得或创建对应 PlayerActor。
3. AccountActor 使用旧 lobbyId + loginTimestamp 做 CAS，占有账号。
4. PlayerActor 加载 DbPlayer；不存在时只在内存创建。
5. PlayerActor 通知 Global 玩家上线。
6. PlayerActor `askAwait(GlobalRootActor)` 查询当前 UserState。
7. Global 的 BattleManagerActorState 若仍有 PlayerId→BattleLocation，则返回 Playing 和 BattleId；否则返回 ActionNone。
8. PlayerActor 回 LoginResponse，GateActor 绑定 PlayerId。

账号和角色严格分离；没有区服，一个账号当前只绑定一个角色。

同账号再次登录时，旧连接与本次新连接都被断开，新客户端再次连接后登录成功。跨 Lobby 冲突由 DbAccount CAS 和旧 Lobby 下线通知处理。

## 7. Player 保存

PlayerActor 独占 DbPlayer，采用消息驱动心跳：

- 每条玩家消息先执行 heartbeat。
- 每 60～120 秒进入一次 minute 分支。
- 距上次 Mongo ACK 成功至少 5 分钟才整体 replace/upsert。
- 新 Player 不在登录路径立即保存。
- 保存失败不推进冷却时间，后续心跳重试。
- 断线、顶号、正常下线和 Lobby 正常退出强制保存，最多重试三次。

仅正常生命周期保证保存。服务器崩溃视为重大程序问题，不为其设计匹配/战局恢复。

## 8. Global

```text
GlobalRootActor
├── MatchActor
├── BattleManagerActor
├── ChatManagerActor
│   └── ChatActor(playerId)
└── RoomManagerActor
    └── RoomActor(battleId)
```

### 8.1 匹配

MatchActorState 使用内存 ArrayDeque 保存 MatchPlayer，其中只含 PlayerId 和 GateActorRef。Match/CancelMatch 在同一 Actor 内串行处理，不写 Redis/Mongo。

配对后 MatchActor 选择健康 Battle，通过 askAwait 请求创建战局；成功后 askAwait BattleManagerActor 注册 GlobalBattleCreated，再向双方 GateActor 推送结果。注册完成后才推送，避免玩家立即发战斗请求时目录尚未就绪。

### 8.2 战局目录和重登录

BattleManagerActorState 保存：

```text
PlayerId -> PlayerBattleLocation(BattleId, Battle NodeId)
BattleId -> PlayerIds
```

Gate 不知道 Battle NodeId。战斗消息全部先到 Global，BattleManagerActor 查目录并保留原 GateActor sender 转发到目标 Battle。

玩家断线不会删除 BattleLocation，只清 Battle 中旧 GateActorRef；因此重新登录时 Lobby 可用 askAwait 查询并恢复当前 BattleId。战斗正常结束后 Battle 通知 Global 删除目录和 RoomActor。

### 8.3 聊天与房间

ChatManagerActorState 保存在线玩家 ChatActor 和展示名摘要；不读取 DbPlayer。RoomManagerActorState 保存 BattleId/PlayerId 到 RoomActor 的映射。RoomActor 只管理聊天成员，不拥有战斗状态。

## 9. Battle

BattleServerActor 是节点根 Actor，并持有两个节点内 ActorId 目录：

```text
BattleId -> BaseBattleActorRef
PlayerId -> BaseBattleActorRef
```

创建战局时生成一个 BaseBattleActor。BattleActorState 直接持有：

- BattleId、BattleType、PlayerIds；
- 3×3 棋盘；
- 当前回合与 eventNum；
- 未准备玩家集合；
- 战局事件；
- PlayerId→GateActorRef 推送目标。

GetBattleInfo、ReadyToStartGame、PlacePieces 和 Concede 都由对应 BaseBattleActor 串行处理。战斗状态不进 Redis。游戏结束只写 DbBattleRecord，然后子 Actor 通知 BattleServerActor 清本地目录并通知 Global 清全局路由/聊天室。

## 10. 持久化边界

| 数据 | 权威拥有者 | 存储 |
| --- | --- | --- |
| AccountId、Lobby 占有、PlayerId 绑定 | AccountActor | Mongo DbAccount |
| 玩家聚合、背包等 | PlayerActor | ActorState + Mongo DbPlayer |
| 在线玩家摘要 | ChatManagerActor | Global 内存 |
| 匹配池 | MatchActor | Global 内存 |
| 玩家当前 Battle 路由 | BattleManagerActor | Global 内存 |
| 聊天房间 | RoomManagerActor/RoomActor | Global 内存 |
| 棋盘、回合、准备和事件 | BaseBattleActor | Battle 内存 |
| 完成战报 | Battle | Mongo DbBattleRecord |
| Insight token | Insight | Redis TTL |

不存在 DbPlayerState、Session Redis、PlayerSummary Redis 或 BattleInfo Redis。进程崩溃后不恢复这些瞬时状态。

## 11. Insight

Insight 是独立管理面，不是 Portal。当前提供默认管理员初始化、`GET /gm/gmUserLogin` 和简化 `GET /gm/executeGmCmd`；Redis 只用于登录 token TTL。后续页面使用 `insight_admin` 命名。

## 12. 构建与启动

所有模块使用 JDK 21 source/target/toolchain，Gradle Wrapper 9.2.0。

```powershell
.\gradlew.bat clean build
.\gradlew.bat :server:shadowJar
```

```powershell
java -jar server/build/libs/server-all.jar --kind=portal --id=1
java -jar server/build/libs/server-all.jar --kind=global --id=1
java -jar server/build/libs/server-all.jar --kind=battle --id=1
java -jar server/build/libs/server-all.jar --kind=lobby --id=1
java -jar server/build/libs/server-all.jar --kind=gate --id=1
java -jar server/build/libs/server-all.jar --kind=insight --id=1
```

同一 jar、同一入口、命令行决定节点类型的约束保持不变。
